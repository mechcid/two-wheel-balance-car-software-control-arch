## 先看这几个结论

1. MPU 驱动仍负责通信；`sensor_app` 仍负责保存和校准六轴数据。姿态、速度、位移在新模块中保存。
2. TIM2 每 2 ms 发出一次中断，ISR 只计数；主循环看到节拍后读取 MPU 并解算。
3. 算法使用相邻成功采集的实际时间间隔，不假设每份数据恰好相隔 2 ms。
4. OLED 同时显示三个姿态角和三轴累计位移；显示函数不推进算法。
5. I2C2 当前是 **100000 Hz，即 100 kHz**。用户反馈当前硬件/CubeMX 配置下，400000 会被标红报错，不能使用。此前将其改为 400000 的做法已撤回，当前配置以用户设置为准。
6. **500 Hz 定时中断、MPU 内部 500 Hz 输出、主循环实际读取频率，是三个不同概念。** 当前还没有证明能每秒读取并解算 500 份新样本。

## 2. 全项目的调用关系

可以先用这幅关系理解每一层：

```text
硬件 MPU6050
    │ I2C 寄存器读写
    ▼
mpu6050              原始 int16_t 六轴计数、温度计数
    │
    ▼
sensor_app           校准后的 g、度/秒、℃、时间戳
    │
    ▼
motion_app           获取实际 dt，调用算法，保存运行统计
    │
    ▼
motion_estimator     四元数、运动加速度、速度、累计相对位移
    │
    ├── main → display_app → oled → 屏幕
    └── telemetry_app → uart_debug → HC-05 → 电脑
```

另有一条时间触发路径：

```text
TIM2 更新中断
    → TIM2_IRQHandler
    → HAL_TIM_IRQHandler
    → HAL_TIM_PeriodElapsedCallback
    → produced 加一

main 的每轮循环
    → MotionApp_Poll 取出节拍，采集并解算
    → Scheduler_Run 执行其他到期任务
```

`motion_estimator` 不知道 MPU 地址，不知道 I2C 句柄，不调用 HAL，不知道 OLED/串口。以后换传感器或 RTOS，只要传入同样单位的三轴加速度、角速度和 dt，这个算法实例仍可以使用。

`motion_app` 是当前 STM32 工程的连接层，迁移平台时需要适配；不能把整个 module 都称为完全平台无关。

## 3. 上电初始化实际做了什么

### 3.1 先初始化板级外设

`main` 先执行 HAL 和系统时钟初始化，再执行 CubeMX 生成的 GPIO、I2C2、USART2、TIM1/3/4/2 初始化。

这些函数建立硬件资源，应用模块才能使用 `hi2c2`、`huart2`、`htim2` 等句柄。

### 3.2 再初始化应用

当前顺序为：

```c
TelemetryApp_Init(&huart2);
SensorApp_Init(&hi2c2, &calibration);
DisplayApp_Init(&hi2c2);
MotorApp_Init(MotorBoard_Init(), HAL_GetTick());

MotionConfig motion_config = MotionEstimator_DefaultConfig();
MotionApp_Init(&htim2, &motion_config);
Scheduler_Init(tasks, TASK_COUNT, HAL_GetTick());
```

逐项解释：

- `TelemetryApp_Init`：启动 UART 接收，注册串口命令。初始化后即可用于观察后续状态。
- `SensorApp_Init`：复制用户校准配置，绑定 I2C2，清空应用样本/统计，然后调用底层 MPU 初始化。
- `DisplayApp_Init`：探测并初始化 OLED，先准备等待页面。
- `MotorApp_Init`：沿用已有电机初始化，默认停止；此次未发送电机运行命令。
- `MotionEstimator_DefaultConfig`：生成一份算法参数，例如滤波截止频率、重力值、缺样阈值。
- `MotionApp_Init`：计算 TIM2 周期、初始化算法实例、请求对应的 MPU 输出率，最后启动 TIM2 中断。
- `Scheduler_Init`：建立其他主循环任务的时间基准。

把 TIM2 启动放在这些初始化之后，可以避免 OLED/MPU 初始化期间的延时产生大量无用节拍。

### 3.3 设备初始化失败时的现有策略

当前 `main` 没有因 `SensorApp_Init` 或 `DisplayApp_Init` 失败立即进入死循环，而是允许串口运行，再由原有任务重试：

- 电机未运行时，每 1000 ms 检查 MPU 是否需要重连。
- 电机未运行时，每 2000 ms 检查 OLED 是否需要重连。

这方便在设备暂时掉线时查看状态。但是重连中的 HAL 等待/MPU 复位延时会阻塞主循环，可能导致采集节拍积压。当前没有将恢复过程改为异步状态机。

## 4. TIM_IT：为什么中断里只加一

### 4.1 这个文件保存的变量

```c
static TIM_HandleTypeDef *source;
static volatile uint32_t produced;
static uint32_t consumed;
```

- `source`：绑定的定时器句柄，当前就是 `&htim2`。
- `produced`：中断累计产生了多少个节拍。
- `consumed`：主循环上一次已经看到多少个节拍。
- `volatile`：提醒编译器，`produced` 可能被中断改变，读取时不能一直使用缓存值。

它没有保存 MPU 样本，也不计算姿态。

### 4.2 实际中断频率怎么算

`TIM_IT_GetTiming` 读取 RCC 的 APB1 配置，以及 TIM2 的 PSC、ARR 寄存器。

STM32F1 的 APB1 分频不为 1 时，TIM2 时钟是 PCLK1 的两倍。当前配置：

```text
PCLK1 = 36 MHz
TIM2 时钟 = 72 MHz
PSC = 71，实际分频数 = 72
ARR = 1999，实际计数长度 = 2000
更新周期 = 72 × 2000 / 72000000 = 0.002 s
更新频率 = 500 Hz
```

PSC 和 ARR 都加一，因为硬件按“寄存器值 + 1”分频/计数。

**动态计算指读取实际配置计算结果。** 当前 motion_app 在启动时保存这个结果，并设置 MPU 输出率；没有提供运行中随意改 PSC/ARR 后自动同步全部模块的接口。

函数目前只支持 TIM2 的内部时钟、向上计数；不能直接拿去支持所有定时器、中心对齐或外部时钟。以后扩展到 TIM1 还需要考虑它位于 APB2。

### 4.3 TIM_IT_Start 中的寄存器操作

- 写 `EGR=TIM_EGR_UG`：产生一次更新事件，让预分频设置生效。
- 清除更新标志：避免把这次人为加载设置当作真实周期中断。
- 将 CNT 清零：从明确的计数起点启动。
- 清空 produced/consumed：建立新的节拍基准。
- 开启 DWT 周期计数器：为主循环测量采集间隔。
- 调用 `HAL_TIM_Base_Start_IT`：正式启动定时器中断。

TIM2 的 IRQ 入口原来已由 CubeMX 生成，因此没有重复编写 `TIM2_IRQHandler`。

### 4.4 为什么没有在中断里直接读 MPU、解算

现有 MPU 驱动使用阻塞式 `HAL_I2C_Mem_Read`。读取时可能等待总线、等待硬件标志或等待超时。

若将它放在高优先级 TIM2 ISR 中，通信异常时可能长时间占住中断；而 HAL 超时又可能依赖其他计时中断更新，处理不好会使整个程序停住。

因此采用“中断记节拍、主循环做工作”的实现。这是我做出的设计选择，也有明确代价：**定时中断准确，但任务实际开始/完成的时刻会受主循环其他工作影响。**

如果用户要求每个样本都有硬件确定的采样时刻，就需要继续设计 DATA_RDY 引脚、FIFO、非阻塞通信/DMA，而不只是将阻塞调用搬进中断。

### 4.5 积压节拍怎么处理

`TIM_IT_TakeTicks` 的主要逻辑是：

```c
uint32_t latest = produced;
uint32_t ticks = latest - consumed;
consumed = latest;
return ticks;
```

若返回 3，说明上次处理后累计到了 3 个节拍。motion_app 只读一次当前最新数据，将 2 个积压节拍计入 `missed_ticks`。

没有 FIFO 时，连续补读三次无法取回过去三份数据，可能只得到同一份当前数据。因此不按节拍次数补做历史积分。

## 5. sensor_app 和 MPU 驱动为什么也有修改

### 5.1 仍保留原始与校准后两份数据

`sensor_app` 私有保存：

- `raw_sample`：原始 int16_t 计数，只用于校准/底层诊断。
- `corrected_sample`：物理单位的六轴、温度及时间戳，外部通过只读指针读取。
- `calibration`：复制自用户配置的偏移和比例。
- `status`：设备状态、成功次数、失败次数、HAL 结果及总线错误。

换算和校准公式仍是：

```text
加速度_g = (原始计数 / 16384 - accel_bias_g) × accel_scale
角速度_度每秒 = (原始计数 / 131 - gyro_bias_dps) × gyro_scale
温度_摄氏度 = 原始温度 / 340 + 36.53 + temperature_offset_c
```

16384 和 131 分别对应现有 ±2g、±250°/s 量程，本轮未添加量程切换。

用户在 main 设置的校准参数仍保留：

```c
.accel_bias_g = {0.01, 0, 0.2},
.accel_scale = {-1, -1, -1},
.gyro_bias_dps = {-1.6, +1.5, -0.6},
.gyro_scale = {1, 1, 1},
.temperature_offset_c = 0,
```

这些是当前配置，不是我替用户重新测得的校准结果。

### 5.2 为什么先检查有没有新数据

新接口 `MPU6050_DataReady` 读取 `INT_STATUS`，检查 DATA_RDY 位。初始化中增加 `INT_ENABLE=1`，以启用对应状态。

这里采用寄存器轮询，没有要求额外接 MPU 的 INT 引脚。

`SensorApp_Update` 现在分三种情况：

| 结果 | 含义 | 做什么 |
|---|---|---|
| `HAL_OK` | 取得一份新样本 | 发布原始/校准样本，成功计数加一 |
| `HAL_BUSY` | DATA_RDY 没有置位，本轮没有新样本 | 不更新样本、不记通信失败 |
| 错误/超时 | 通信失败，或设备已经离线 | 不发布新数据，供上层判断是否可用 |

这处 `HAL_BUSY` 被用作“尚无新样本”的约定，阅读此模块时不要把它都理解成硬件总线出错。

只在取得新数据后才推进算法，可避免将同一份样本多次当成新测量。

### 5.3 MPU 输出率设置

新增 `MPU6050_SetOutputRate`。DLPF=3 时，驱动按 1 kHz 基础速率选择整数分频：

```text
内部输出率 = 1000 / (SMPLRT_DIV + 1)
```

例如请求 500 Hz：

```text
整数分频数 = 2
SMPLRT_DIV = 1
实际输出率 = 500 Hz
```

请求任意频率不一定能精确实现，代码取接近 `1000 / 请求频率` 的合法整数分频，并返回实际值。合法分频数是 1～256。

`requested_rate_hz` 保存上层想要的频率；`actual_rate_hz` 保存最近成功设置的实际频率。重连先按驱动默认的 100 Hz 初始化，然后重新应用保存的要求。

这个接口改变的是 **MPU 内部输出率**，不是 I2C 的传输时钟。

### 5.4 校准校验补充了什么

为了保留用户的三轴反号，负比例仍允许使用。同时补充拒绝：

- 比例为 0：会把整轴输出变成 0，失去测量意义。
- 比例绝对值超过 10：避免极端配置。
- 非有限数，例如 NaN、无穷大：无法参与正常运算。

并未自动修改用户的正常校准参数。

### 5.5 哪些底层行为原样保留

- 探测 0x68/0x69 和 WHO_AM_I 身份检查。
- ±2g、±250°/s 量程。
- DLPF=3。
- 现有读取 15 字节、使用前 14 字节的尾字节规避方案。
- 阻塞式 HAL I2C 通信及超时。

尾字节规避方案是之前的板端诊断结果，目录迁移时没有删除它，也没有把它解释成所有 STM32 都存在的普遍问题。

## 6. motion_app：它到底额外做了什么

`motion_app` 是采集和算法之间的单实例适配层。

### 6.1 私有变量

| 变量 | 用途 |
|---|---|
| `estimator` | 一份 MotionEstimator，包括配置、姿态、积分结果和滤波历史 |
| `status` | 运行统计、定时器信息、最近一次 dt 和时间戳 |
| `last_cycles` | 上次成功读取开始时的 CPU 周期计数 |
| `last_ms` | 上次成功读取开始时的毫秒时间 |
| `started` | 本模块是否已成功启动 |
| `have_time` | 是否已有上一份成功样本可用于计算 dt |

`static` 表示这些状态由这个源文件持有，不把变量名字直接暴露给其他文件。外部通过访问函数读取结果。

### 6.2 MotionApp_Poll 的完整流程

1. 没启动，直接返回。
2. 取出 TIM2 积累的节拍；没有新节拍，直接返回。
3. 节拍多于一个时，将多出的数量计入 missed_ticks。
4. 记录本次开始采集的毫秒和 CPU 周期计数。
5. 调用 `SensorApp_Update`。
6. 无新数据：no_data 加一，保留上次成功时间，不调用算法。
7. 失败：failures 加一，使算法结果无效、速度归零、标记轨迹中断，取消上一份时间基准。
8. 成功：计算相邻成功采集的实际 dt，读取校准样本，传给 `MotionEstimator_Update`。
9. 保存 dt、时间戳和解算统计。

为什么没有再加一个 `sample_task`？因为 motion_app 已经负责这次采集，再保留原来的 10 ms 采集任务会产生两个采样入口，彼此消耗新数据并破坏时间间隔计算。

### 6.3 实际 dt 为什么用 DWT

`HAL_GetTick()` 通常只有毫秒分辨率。2 ms 附近的实际间隔可能为 1.7、2.3 ms，仅用整数毫秒不够细。

DWT 是 Cortex-M3 的 CPU 周期计数器。当前 72 MHz 下：

```text
dt_秒 = (本次周期计数 - 上次成功采集周期计数) / 72000000
```

无符号减法可处理一次计数回绕。32 位 DWT 在 72 MHz 下约每 59.65 秒回绕一次，所以长间隔还检查毫秒时基：超过 1 秒时采用毫秒差值，避免长时间暂停被误认为一个很小的 dt。

`max_dt_s` 的默认值是 0.05 秒，因此这样的长缺样会被算法拒绝积分。

**这个时间是 STM32 主控开始读取数据的时间，不是 MPU 内部准确的采样时间。** 两套时钟未同步，当前没有硬件采样时间戳。

### 6.4 访问接口为什么返回 const 指针

```c
const MotionState *motion = MotionApp_GetState();
```

它让调用者读取同一份结果，不需要复制整个结构体；`const` 阻止通过这个指针正常写入状态。

显示和串口因此可以共享结果，但不能各自再次积分。这些接口目前默认在主循环使用，没有提供中断/RTOS 并发访问的快照锁。

## 7. motion_estimator：按步骤读懂算法

这是新增文件中数学最多的一个。可以先理解输入、输出和每一步的目的，再看四元数公式。

### 7.1 输入与输出

输入：

```text
accel[3]：校准后的加速度输出，单位 g
 gyro[3]：校准后的角速度，单位度/秒
    dt_s：相邻成功样本的间隔，单位秒
```

输出 `MotionState`：

| 成员 | 含义 |
|---|---|
| `q[4]` | w、x、y、z 四元数，描述机体到参考系的旋转 |
| `linear_mps2[3]` | 去掉重力后的参考系运动加速度，m/s² |
| `velocity_mps[3]` | 参考系三轴速度，m/s |
| `position_m[3]` | 参考系累计相对位移，m |
| `valid` | 最近一次解算有效 |
| `accel_trusted` | 本帧通过重力反馈门限 |
| `discontinuity` | 轨迹曾因异常或缺样发生中断 |

`valid` 不能解释为“位移准确”；`accel_trusted` 也不能解释为“加速度完全没有运动成分”。

### 7.2 为什么又出现了 accel_sign=-1

用户已将 SensorApp 的三轴加速度整体取反，水平静止时显示约 −1g。标准姿态公式内部需要使用静止时沿向上方向为 +1g 的比力。

因此在算法入口做：

```c
a[i] = config.accel_sign * accel[i];
```

默认 `accel_sign=-1`，只改变算法内部输入，SensorApp 的数据和用户的符号设置不变。

这个处理采用了一个明确假设：**三轴反号是加速度输出整体符号约定；机体姿态仍沿当前陀螺仪的右手轴定义。**

它没有自动完成“模块轴 → 车体轴”的安装方向映射。三轴同时反号并不等于一个物理安装旋转。当前参考系 Z 向上，X/Y 根据初始姿态及 yaw=0 建立，还不能直接认定 X 就是车头方向。

如果需要严格使用用户定义的车头/左右方向，后续应明确模块的安装方向，再给加速度和陀螺仪应用一致的轴旋转。此次没有测得或擅自定义这组映射。

### 7.3 第一次采集为什么特殊

初始化将四元数设为 `{1,0,0,0}`，其他状态清零，但这只是“尚未取得姿态”的初始状态。

第一次取得模长接近 1g 的加速度后：

1. 用重力方向建立 roll 和 pitch。
2. 初次 yaw 设为 0。
3. 将倾角转换成四元数。
4. 将滤波历史初始化为当前测量，避免滤波器从 0 慢慢爬升造成启动假信号。
5. 初速度设为 0；这份数据不做积分。

因此启动时应尽量静止。如果启动时加速度模长明显偏离 1g，算法暂不建立姿态。

这里无法根据 IMU 判断小车上电瞬间是否已有平移速度，初速度为零是一项假设。

### 7.4 正常更新时先处理陀螺仪

陀螺仪告诉我们每秒绕各轴转多少度。先乘约 0.0174533，将度/秒变为弧度/秒；再按 dt 推进四元数。

四元数归一化，是让四个分量重新满足单位长度，避免反复运算的小数误差导致旋转不再保持正常比例。

选择四元数是为了让三个轴的连续转动能够一致地组合。只分别累加三个欧拉角，在不同轴共同转动时并不等价于真实旋转。

Roll/Pitch/Yaw 是便于查看的结果，`MotionEstimator_GetEuler` 在显示/查询时再把四元数转换成它们；没有每 2 ms 都计算一遍欧拉角。

### 7.5 加速度低通和重力反馈

`gravity_lpf[3]` 保存加速度的低通历史。它使快速抖动对倾角纠正的影响减小。

当前低通写法：

```text
k = 2π × 截止频率 × dt
gain = k / (1 + k)
滤波后值 += gain × (当前输入 - 滤波后值)
```

截止频率较低：曲线更平滑，响应更慢。较高：响应更快，噪声也更容易通过。dt 参与系数计算，所以没有暗中使用固定 500 Hz 系数。

`gravity_body` 根据四元数计算“参考系的向上方向，在当前机体轴中应该指向哪里”。算法把它与滤波测量方向比较，用叉积得到方向误差，再按 `correction_gain` 补偿角速度。

可以直观理解为：

> 陀螺仪负责跟踪刚刚发生的转动；重力方向逐步纠正累计出来的倾角偏差。

这属于非线性互补反馈。此次没有引入完整卡尔曼滤波，也没有完整照搬第三方 Mahony 库，没有额外积分估计陀螺仪零偏。

### 7.6 为什么不一直相信加速度

正常更新时，重力反馈需要通过两道门限：

- 当前加速度模长与 1g 的差，小于 `accel_tolerance_g`，默认 0.12g。
- 滤波测量方向与预测方向差小于 30°。

不通过时，本帧暂停加速度纠正，但继续使用陀螺仪推进姿态。

这只能减少明显运动造成的误导，不能消除“持续小加速度被认为倾斜”的问题。角速度零偏仍可能导致姿态漂移，yaw 尤其没有重力参考来长期校正。

### 7.7 重力扣除为什么要先旋转

机体坐标随小车倾斜。小车倾斜后，重力可能同时出现在 X/Y/Z 三个通道。

`rotate_world` 先将内部比力旋转到参考坐标；再把 g 换算成 m/s²，并从参考系 Z 中减去 9.80665。

```text
机体比力_g
  → 按 q 旋转到参考系
  → 乘 9.80665，变成 m/s²
  → 参考系 Z 减 9.80665
  → 得到运动加速度
```

在这一步之后只扣参考系 Z 是合理的，因为参考系 Z 已定义为竖直向上。直接在未旋转的原始机体 Z 通道上始终扣 g，则无法处理倾斜。

### 7.8 速度和位移怎么累计

运动加速度还经过另一组低通，使用 `linear_cutoff_hz`，默认 20 Hz。

然后用相邻两份加速度的平均值求速度增量，再用相邻两份速度的平均值求位移增量：

```text
新速度 = 旧速度 + (旧加速度 + 新加速度) / 2 × dt
新位置 = 旧位置 + (旧速度 + 新速度) / 2 × dt
```

这就是梯形积分。`previous_accel[3]` 保存上一份加速度，供下一次更新使用。

速度与位置都在固定参考系中保存，不会随着屏幕刷新次数增加。OLED 每 200 ms 显示一次，不表示每 200 ms 才积分一次。

### 7.9 缺样与非法输入的处理

遇到通信失败、非法数值、异常 dt 或 dt 大于 `max_dt_s` 时：

- `valid=false`。
- `discontinuity=true`。
- 速度归零。
- 保留上次姿态和位置。

下一份可信测量重新建立 roll/pitch，沿用上次 yaw 和位置，滤波历史重新建立，不补偿缺失期间的运动。

这是让程序恢复运行的策略，不是恢复丢失运动的算法。因此 GAP 保留，提醒观察者轨迹已不完整。

### 7.10 静止声明和归零的区别

`MotionEstimator_SetStationary(true)`：外部明确告诉算法“现在确实没动”。更新时仍处理姿态和加速度，但将速度保持为零、位置保持不变。

为什么不自动判定？匀速运动时也可能测得零角速度及接近 1g 的模长。仅凭 IMU 将其自动当成静止，会把真实匀速误消掉。

`MotionEstimator_ResetPosition`：把速度、位置和 GAP 标记清零；保留当前姿态、校准及静止声明。它意味着主动设定新原点，并假设此刻初速度为零。

移动前需要取消静止声明。归零命令本身不会取消静止声明。

### 7.11 几种容易看不懂的 C 写法

下面只解释代码写法，不改变算法含义。

```c
MotionConfig c = config ? *config : MotionEstimator_DefaultConfig();
```

- `config` 是配置结构体的地址。
- `*config` 是地址指向的整个配置结构体。
- 三目表达式的含义：有传入配置就复制它；没有传入就取得默认配置。
- `c` 是结构体副本，后续配置的生命周期不依赖调用者的局部变量。

```c
*e = (MotionEstimator){
    .config = c,
    .state = {.q = {1, 0, 0, 0}}
};
```

- `e` 是外部提供的算法实例地址。
- `(MotionEstimator){...}` 构造一个结构体值，指定的字段使用写出的值。
- 没写出的成员在这个初始化表达式中自动为零，所以速度、位置、标志、历史值等清零。
- `*e = ...` 把整个初始结构体写入调用者提供的实例。
- `.state = {.q = ...}` 是给结构体中嵌套的另一个结构体指定初值。

这与单纯声明一个局部变量后没有赋值不同；初始化表达式中省略字段有明确的清零规则。

```c
MotionState *s = &e->state;
```

`s` 指向实例内部的 state。修改 `s->velocity_mps` 就是在修改 `e->state.velocity_mps`，没有新建第二份结果。

```c
bool first = !s->valid;
```

这里 first 表示“当前没有可继续推进的有效姿态”，既包括首次启动，也包括通信/缺样失败后的恢复入口，不只表示程序启动后的第一个函数调用。

```c
memcpy(e->gravity_lpf, a, sizeof(a));
memset(s->velocity_mps, 0, sizeof(s->velocity_mps));
```

前一句复制当前三轴值到滤波历史；后一句将速度数组清零。当前两处数组的长度/数据类型都是确定的，没有动态申请内存。

几个数学辅助函数的用途：

| 写法 | 用途 |
|---|---|
| `sqrtf(x)` | 单精度平方根；用于向量长度、归一化 |
| `fabsf(x)` | 单精度绝对值；比较误差幅度 |
| `isfinite(x)` | 检查是否为正常有限数，排除 NaN/无穷大 |
| `atan2f(y, x)` | 根据两个方向分量求角度，能区分象限 |
| `asinf(x)` | 从正弦值求角度；输入需在 −1～1 内 |
| `clamp(x, -1, 1)` | 避免小数舍入把反正弦输入变成 1.000001 等非法值 |
| 向量点积 `dot` | 对两个单位方向，等于夹角余弦；0.8660254 约为 cos(30°) |
| 向量叉积 `error` | 表示两个方向的旋转偏差方向，供倾角反馈使用 |

`f` 后缀表示单精度版本，当前结构体也使用 float。它不表示芯片有浮点硬件；Cortex-M3 由编译器/数学库执行软件浮点运算。

## 8. 算法参数在哪里改，各自影响什么

当前 main 取得默认配置后传入初始化，后续可以在该处明确改参数：

```c
MotionConfig motion_config = MotionEstimator_DefaultConfig();
motion_config.accel_cutoff_hz = 10.0f;
motion_config.linear_cutoff_hz = 20.0f;
MotionApp_Init(&htim2, &motion_config);
```

| 参数 | 当前默认值 | 修改后的主要影响 |
|---|---:|---|
| `accel_sign` | −1 | 接入 SensorApp 的整体加速度符号；不能当作任意安装轴映射 |
| `gravity_mps2` | 9.80665 | g 到 m/s² 换算及重力扣除基准 |
| `correction_gain` | 2 | 重力方向纠正强度；过大时运动加速度更容易影响倾角，设 0 则关闭反馈 |
| `accel_cutoff_hz` | 10 Hz | 重力参考的平滑程度和响应延迟 |
| `linear_cutoff_hz` | 20 Hz | 运动加速度的平滑程度和积分响应延迟 |
| `accel_tolerance_g` | 0.12g | 加速度模长反馈门限，不是传感器标称精度 |
| `max_dt_s` | 0.05 秒 | 可接受的相邻样本最大间隔，不是任务调度周期 |

参数是配置初值，不是已经根据真实小车运动优化好的最佳参数。初始化会检查参数范围并复制配置。

校准参数仍在 main 的 `SensorCalibration calibration` 中；它与滤波参数是两组不同配置。校准处理每轴零偏/比例，滤波处理时间变化和姿态融合。

## 9. OLED 页面具体改了什么

旧页面通过 gravity/angular 显示加速度或角速度；新页面改为：

```text
RPY deg   XYZ mm
R -12.3 X   +123
P +45.7 Y     -5
Y+180.0 Z     +0
```

- R：roll，绕 X 轴的姿态角。
- P：pitch，绕 Y 轴的姿态角。
- Y：yaw，绕 Z 轴的相对航向角。
- 右列 X/Y/Z：参考系三轴累计相对位移，单位毫米。

屏幕每行只有 16 个字符，所以左侧“标签 + 角度”占 7 列，中间空 1 列，右侧“标签 + 位移”占 8 列。

### 9.1 显示函数的输入变了

原来：

```c
DisplayApp_Render(const SensorSample *sample, bool available);
```

现在：

```c
DisplayApp_Render(const MotionState *motion,
                  const float degrees[3], bool available);
```

main 的 display_task 先取得欧拉角及算法结果，再传给显示。显示模块不自己采集、不自己调用 Update，不因画面刷新重复积分。

`available` 由 main 判断设备就绪、样本存在且未超过 500 ms，同时检查解算时间；显示模块再检查 `motion->valid`。

### 9.2 数值格式为什么额外写了两个函数

`format_angle` 将角度拆成整数和一位小数；`format_position` 将米转为毫米并舍入。

原因是当前没有启用浮点 printf。直接使用 `%f` 会引入更多格式化代码，而这块工程的 64 KiB Flash 已接近用满。

还有两种异常显示：

- 超出位移栏位范围（±999999 mm）：显示 `+OVF` 或 `-OVF`。
- 非有限数值：显示 `--`。

这样不会把超长字符串截成一个看似正常但数值错误的结果，也会覆盖整行，防止短的新数字后面留下旧字符。

### 9.3 页面状态

- 正常：标题 `RPY deg   XYZ mm`。
- 轨迹中断：标题 `RPYdeg XYZmm GAP`。
- 无有效或新鲜测量：`POSE waiting...`，三行数值为 `--`。

OLED 底层仍用 1024 字节显存和分块发送。此次只改变显示内容，没有另写屏幕底层驱动。

## 10. 串口增加了哪些命令和状态

命令格式沿用用户 UART 模块：`@` 开头、CRLF 结尾。

| 命令 | 作用 |
|---|---|
| `@pose` | 输出频率、dt、统计、姿态、运动加速度、速度、位置 |
| `@pzero` | 速度/位置归零，清除 GAP；不重置姿态 |
| `@still:1` | 外部明确声明静止 |
| `@still:0` | 取消静止声明 |
| `@stream:2` | 连续输出姿态与位置 |
| `@stream:1` | 连续输出原有六轴数据，当前默认值 |
| `@stream:0` | 关闭连续上报，便于单次状态查询 |

HC-05 助手中输入命令时需加 `\r\n`，例如 `@pose\r\n`。

姿态帧：

```text
POSE,时间_ms,valid,roll_mdeg,pitch_mdeg,yaw_mdeg,X_mm,Y_mm,Z_mm
```

度乘 1000 变成毫度，米乘 1000 变成毫米，避免浮点格式化。超出整数范围时进行饱和输出，不做越界浮点到整数转换。

查询中的计数含义：

| 字段 | 含义 |
|---|---|
| `ok` | motion_app 成功完成解算的次数 |
| `missed` | 主循环没有逐个处理的 TIM2 节拍数量，不等同于 MPU 丢帧数 |
| `nodata` | 轮询时 DATA_RDY 尚未置位的次数 |
| `fail` | 解算/采集适配失败次数；设备已离线时的调用也计入，不等同于实际 I2C 事务失败数 |
| `dt_us` | 上次成功读取交给算法的间隔，微秒 |
| `TIM hz_m` | 计算的定时频率乘 1000 |
| `MPU hz_m` | 最近取得的 MPU 实际输出率乘 1000 |

浮点计算再截断为整数时，`TIM hz_m` 可能显示 499999，而按寄存器整数关系计算仍是 500 Hz；这一位差值不是 TIM2 被配成了 ARR=2000。

## 11. CMake 和 VSCode 的修改原因

### 11.1 为什么移动文件后要改 CMake

CMake 的源文件列表记录了真实路径。移动文件但不更新路径，编译就会找不到原来的 `.c/.cpp`。

此前迁移时改成分层路径；现在恢复为 `module/src/文件名`，头文件搜索路径恢复为：

```cmake
module/inc
```

因此源文件可以继续写：

```c
#include "mpu6050.h"
#include "motion_app.h"
```

没有要求在每个 include 中填写多层相对路径。

算法的单文件优化配置也恢复为 `module/overlay_app/src/motion_estimator.c`，优化选项本身保留。

### 11.2 为什么修改 Debug 优化

姿态代码引入平方根、三角函数和浮点运算。原来的 Debug 使用 -O0，加入算法后超出链接脚本规定的 64 KiB Flash。

此次在顶层 CMake 追加：

- Debug 应用和 HAL：`-Og`，保留 `-g3` 调试符号。
- `motion_estimator.c`：单文件 `-O2`，加快 Cortex-M3 上的软件浮点运算。
- Release 其他文件：继续使用原有 `-Os`。

编译命令中可能同时看到 `-O0 -g3 ... -Og`，同一优化选项以最后一个为准；算法文件末尾还有 `-O2`。

未扩大链接脚本容量，没有因为调试器识别为 128 KiB 就擅自把 64 KiB 上限改掉。

代价是部分局部变量可能被优化掉，单步顺序也可能与源代码顺序不同。若后续需要完全无优化调试，需要先精简固件体积。

### 11.3 为什么只改 settings.json

`.vscode/settings.json` 中的备用 includePath 曾同步改为两个新目录；本次恢复为原来的 `module/inc`。

Debug/Release 的 `compile_commands.json` 通过重新配置生成，包含移动后的文件路径和编译参数，帮助 VSCode 正确解析代码。

`tasks.json` 的构建/下载流程、`launch.json` 的 DAP 调试配置及 `extensions.json` 本轮不需要更改；已有下载调试入口继续使用。

## 12. I2C 参数的纠正与频率限制

### 12.1 当前明确使用 100 kHz

当前两个配置一致：

```c
/* Core/Src/i2c.c */
hi2c2.Init.ClockSpeed = 100000;
```

```text
# balance_car.ioc
I2C2.ClockSpeed=100000
```

用户反馈 400000 在当前 CubeMX/硬件配置中会标红报错。此前为了增加采集吞吐将其修改为 400000，没有先确认该配置是否可用，这个修改不合适。现在按用户的 100000 保留，相关文档同步纠正。

这里记录的是当前工程的实际约束，没有掌握 CubeMX 的具体报错信息，因此不推断所有型号/配置是否支持其他速率。

### 12.2 为什么 100 kHz 下不能保证读满 500 Hz

I2C 除了数据，还需要设备地址、寄存器地址、ACK 和起止过程。本项目每次读取六轴包含 15 字节事务，前面还有一次数据就绪查询，OLED 也使用同一总线。

只按总线位数估算，一份采集的两次事务就已接近或超过 2 ms，再加软件等待和屏幕传输，主循环可能跳过部分节拍。

所以当前保持：

```text
TIM2：500 Hz 硬件节拍
MPU：请求匹配 TIM2 的内部输出率，当前目标 500 Hz
I2C2：100 kHz，实际采集吞吐受限
算法：按成功采样的实际 dt 更新
```

后续应根据实际采集次数、missed/nodata 和 dt 决定如何优化，不通过擅自提高 I2C 时钟解决。可讨论减少查询开销、FIFO、非阻塞传输、降低读取频率或减少屏幕占用，但本轮未实现这些后续方案。

## 14. 这些结果目前能用来做什么

可以用于观察倾角、相对转动方向、扣除重力后的加速度趋势，以及短时间相对积分实验。

还不能把累计位置直接当作可靠定位结果：

- 残余加速度零偏会被积分成速度，再被积分成位置。
- 姿态误差会把一部分重力错误当成运动加速度。
- MPU6050 的六轴测量无法提供稳定的绝对航向。
- 起始速度、模块安装到车体的轴映射尚有假设。
- 通信缺样期间的运动不能恢复。

例如固定残余误差只有 0.01g，静止积分 10 秒也可能产生约 4.9 米位置误差。显示跳动变小，不等于位移误差也变小。

平衡车最终仍应结合编码器、轮径等约束平面速度和路程。此次没有将 IMU 位移融合进电机闭环，也没有完成整车平衡控制。
