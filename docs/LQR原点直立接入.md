# LQR 原点直立控制（软件接入）

当前只实现固定位置、固定航向的直立模式，不包含轨迹控制。默认上电停用。已完成文末记录的停机板上验证，未进行实车闭环验证。

## 模块和执行顺序

- `module/overlay_app/src/lqr_app.c`：误差组装、离散反馈、力矩换算、限幅、启停和故障锁存。
- `module/overlay_app/inc/lqr_app.h`：配置、状态和 C 接口。
- `module/overlay_app/inc/lqr_gain.h`：生成的单精度 2×6 增益及 5 ms 周期。
- `tools/generate_lqr.py`：读取原始 JSON 的模型和权重，精确零阶保持离散化动力学及连续积分代价，保留交叉项 Nd，用 DARE 求增益。
- `docs/reference/LQR直立离散参数.json`：物理参数、来源、离散矩阵、权重、增益和验证范围。

主循环优先处理 200 Hz IMU，然后按固定微秒截止时间进行 200 Hz 编码器/整车状态更新，随后计算 LQR 并立即写 PWM。积压时只处理当前帧，不补算历史控制。原来的 10 ms 状态调度已移出普通任务表。

`MotorApp_ApplyDuty()` 立即施加占空比，不重新读取编码器、不改变反馈序号和采样时间。原有 `MotorApp_SetDuty()` 保留开环命令下一周期输出的行为。状态模块仍独占电机反馈回调，LQR 不在回调内部控制电机。

## 状态与换算

启用时只捕获一次 `(x_hold,y_hold,psi_hold)`，把当前位置作为原点和固定航向。控制期间不清零里程计。

误差顺序为 `[e_x,e_psi,theta,e_xdot,psi_dot,theta_dot]`，其中位置和速度投影到固定目标航向，航向差归一化。该控制器不恢复横向位置。零点和方向沿用项目现有定义。

反馈 `tau = -Kd E`，左右轮分别输出 N·m，计算结果不再乘 Ts。电机按 12 V 名义供电换算：

```
omega_relative = encoder_rpm * 2*pi/60
raw_duty = (tau + 0.01139*omega_relative) / (0.03677*12)
duty = clip(raw_duty, -0.40, +0.40)
```

此处使用相对车身的编码器转速，不加俯仰角速度；整车速度估计的俯仰补偿仍在状态模块内完成。`estimated_nm` 是按最终占空比反算的模型估计，并非电流传感器测得的实际力矩。停机或故障后，误差、力矩和模型估计保留为最后诊断值，duty 清零；必须结合 mode 查看。

## 接口与命令

- `LqrApp_Init()`：初始化，默认停用。
- `LqrApp_Start()`：只允许从停用且电机停止的状态启动，要求有效、新鲜、同步的状态，记录固定参考。
- `LqrApp_Update()`：在新状态发布后调用，相同序号不重复计算。
- `LqrApp_Poll()`：每轮主循环监测失效和超时。
- `LqrApp_Stop()`：退出闭环、停止电机并清除 LQR 故障锁存。

串口命令以 CRLF 结束：

| 命令 | 行为 |
|---|---|
| `@lqrstart` | 显式启动；下一份完整周期状态开始输出 |
| `@lqrstatus` | 查询模式、故障、更新次数、周期、数据年龄、参考、六维误差、请求力矩、模型力矩、占空比和饱和状态 |
| `@mstop` | 同时退出 LQR 并停机；故障后必须明确执行停止才能再次请求启动 |
| `@mdrive` | LQR 工作期间拒绝，避免手动占空比覆盖闭环 |

模式值：0 停用，1 直立保持，2 故障。故障位：1 状态异常，2 周期异常，4 超出局部范围，8 输出异常。

LQR 自己刷新电机命令，无须发送 `@mkeep`；串口断开不会终止自主保持。无独立硬件看门狗保证主循环完全卡死时的停机，本次软件超时检查依赖主循环继续执行。

## 当前软件边界与验证

默认配置位于 `LqrApp_DefaultConfig()`：12 V、占空比 0.40、允许启动俯仰 0.10 rad、退出俯仰 0.35 rad、纵向偏移上限 0.25 m、航向偏差上限 0.50 rad。这些是可调整的软件调试边界，不代表已实测的捕获范围。

状态和姿态最大年龄为 7.5 ms；控制超过 7.5 ms 未更新，或相邻状态周期不在 2.5–7.5 ms 内，退出闭环。允许的抖动范围仅是软件故障判定，不代表范围内所有延迟已通过稳定性验证。状态估计因缺帧失去连续性后，单独清除 LQR 故障不能修复里程/姿态，须恢复估计后才可启动。

5 ms 理想轮轴力矩零阶保持线性模型，使用固件单精度 Kd 后闭环谱半径约 0.996551373087。尚未完成 PWM/电机动态、滤波和总延迟、饱和下的非线性闭环验证，也未验证实机总线吞吐与调度抖动。

验证命令：

```
python3 tools/generate_lqr.py
bash tests/lqr/run.sh
bash tests/motor_open_loop/run.sh
bash tests/status_state/run.sh
bash tests/imu_timing/run.sh
cmake --preset Debug
cmake --build --preset Debug
```

主机测试覆盖参考投影、角度跨界、反馈符号、转速单位、饱和、无效数值、默认不启动、重复帧、时钟回绕、故障锁存、超时、倾角越界、输出失败，以及立即输出不重复采样。

## 2026-10-17 板上排查与屏幕刷新修复

通过无线 CMSIS-DAP 读取状态并比对板上程序，确认此前启动拒绝时整车 `faults=0x0A`、`valid=false`，姿态 `discontinuity=true`。这是姿态/位置连续性锁存异常，不是仅有 7.5 ms 新鲜度比较失败。最初触发连续性丢失的具体事件未能从现有累计计数确定；断点调试可能扰动 I2C 事务，不能据此断言唯一根因。复位后连续运行的验证中未复现。

屏幕初始化成功但发送受饿：在刷新入口读到剩余约 2.37 ms，小于此前所需的 2.5 ms。LQR 停用时，新增的 200 Hz 整车状态工作仍会占用主循环时间，因此旧屏幕预算不再匹配。将 OLED 数据块从 16 字节缩为 8 字节，128 块覆盖整屏，预算改为 1.7 ms；没有降低 IMU 或状态更新频率，也没有放宽控制器新鲜度检查。

最终固件所有可加载节校验一致。复位后约 30 秒读到：

- IMU 更新 5973 次，missed_periods=0、no_data=0、failures=0。
- 整车状态 valid=true、faults=0，姿态 discontinuity=false。
- OLED ready=1、error=0、transfers=753，128 个待刷新标记全部清零；用户确认屏幕恢复正常刷新。
- LQR_DISABLED，左右 PWM 比较寄存器均为 0，PA15/STBY 为低。

新增 `@lqrcheck`（CRLF），只报告状态，不启动电机：整车有效位/故障位、状态与姿态年龄、俯仰、左右轮反馈有效位、序号匹配、姿态有效位和连续性标志。`@lqrstart` 被拒绝时也打印这些信息。当前默认启动倾角阈值仍为 0.10 rad（约 5.73°），采样正常但倾角过大仍会拒绝。

新增 `bash tests/oled/run.sh` 验证 8 字节块的整屏覆盖、字符边界脏标记、重复内容不重发及故障重初始化。编译及 OLED/LQR/IMU/状态主机测试通过。本次没有启动电机，未验证闭环运行时的执行耗时或稳定性。

## Trace 模块拆分

当前记录由独立 `trace_app` 管理，业务运行/有效性/新序号共同决定采样，停止或异常自动写终止事件并冻结。详见 [Trace 运行记录模块](understanding/Trace运行记录模块.md)。原有导出工具已迁移到新结构（schema_version=3），历史试验 JSON 保留原格式。

当前 LQR 和 IMU 在 main 中分别创建、初始化有类型的 Trace 实例，由 Debug 统一轮询；LQR 不依赖 Trace。两秒试验由 debug_app 协调。`LqrApp_Init(&config, &tuning)` 分别接收执行器/限制配置和独立 `LqrTuning`，默认 pitch_rate_scale 保留为 0.5。详见上面的 Trace 文档。
