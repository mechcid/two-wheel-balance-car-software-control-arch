# MPU6050 模块架构笔记

## 1. MPU6050 直接测量什么

MPU6050 提供三轴加速度计读数、三轴角速度和芯片内部温度。X、Y、Z 是传感器自身的轴，随模块一起转动，不是始终固定在地面的三个方向。

- **陀螺仪**：测量绕自身三个轴的角速度，常用单位为 °/s 或 rad/s。
- **加速度计**：测量三个轴上的比力，常用单位为 g 或 m/s²。
- **温度计**：测量芯片内部温度，不能直接当作准确的环境温度。当前采集接口未将温度放入样本。

姿态角、速度和位移需要软件根据读数估计。角速度的三个分量也不能在任意三维姿态下直接分别积分成横滚角、俯仰角和偏航角；完整姿态更新需要正确的旋转运动学关系，例如通过四元数进行计算。

## 2. 为什么静止时 Z 轴也有约 1 g

模块静止时，运动加速度为零。假设模块水平、Z 轴向上，且软件没有额外反转坐标轴，理想读数为 X ≈ 0、Y ≈ 0、Z ≈ +1 g。

加速度计内部有微小质量块。桌面支撑模块时，外壳通过内部结构支撑质量块，使它不随重力自由下落。传感器检测到这种非重力作用，因此静止时有约 1 g 的读数；自由落体时反而接近零。

比力可以理解为单位质量受到的非重力作用力。用同一坐标系表示各量时：

$$
\mathbf f = \mathbf a - \mathbf g
$$

其中，$\mathbf f$ 为理想加速度计读数，$\mathbf a$ 为运动加速度，$\mathbf g$ 为重力加速度向量。取向上为正，静止时 $a_z = 0$、$g_z = -g$，因此 $f_z = +g$。

| 场景 | 理想读数 |
| --- | --- |
| 水平静止，Z 轴朝上 | Z ≈ +1 g |
| 静止倒置，Z 轴朝下 | Z ≈ −1 g |
| 静止倾斜 | 重力相关读数分配到三个轴上，合成大小约为 1 g |
| 自由落体 | 三轴加速度计读数接近零 |
| 水平、Z 轴朝上且向上加速 | Z 大于 +1 g |

## 3. 测量误差与零偏校准

IMU 的测量存在零偏、噪声，以及随温度和时间变化的误差。即使精度较高，也需要考虑零偏校准，不能默认静止时的输出就是理想值。

这里的校准并不意味着将静止时的所有读数清零：陀螺仪在静止时的理想角速度为零，而加速度计仍会测得与重力有关的分量。

校准后的静止加速度计读数应与已知放置姿态相符，三轴合成大小应接近 1 g。**零偏校准与去除重力分量是两件不同的事。**

## 4. MPU6050 在当前项目中的作用

MPU6050 能够测量三轴加速度和三轴角速度。在当前平衡车项目中，这些数据主要用于姿态估计和角速度反馈。

需要区分两个职责：**MPU6050 采集模块提供测量数据，姿态估计模块根据这些数据计算姿态。** 俯仰角、横滚角和偏航角并不是当前采集接口直接提供的测量值。

### 4.1 不依赖加速度积分估计速度和位移

在当前项目中，不宜仅依靠 MPU6050 的加速度积分来估计长期速度和位移。

加速度测量中的零偏、噪声，以及姿态误差导致的重力补偿误差，都会影响积分结果。加速度积分得到速度时，误差会累积；再次积分得到位移时，误差还会进一步放大。因此，单独依靠 MPU6050 难以获得稳定可靠的长期速度和位移估计。

### 4.2 加速度计为倾角提供长期参考

在车体静止或运动加速度较小的情况下，可以利用加速度计测得的重力方向，估计车体的俯仰角和横滚角，为姿态估计提供长期参考。

但加速度计无法直接区分重力与运动产生的加速度。车体明显加减速或受到振动时，不能直接把测量结果全部当作重力来计算倾角，需要结合陀螺仪数据进行融合。

### 4.3 俯仰、横滚与偏航的区别

- **俯仰角和横滚角**：可以结合陀螺仪的短期变化与加速度计提供的重力方向进行估计。在校准和融合合理、运动干扰可控的条件下，能够保持相对稳定。
- **偏航角**：无法通过重力方向获得校正。仅使用 MPU6050、且没有其他航向参考时，偏航估计主要依赖陀螺仪积分，误差会随时间累积并产生漂移。
- **三轴角速度**：可以直接用于后续计算和控制，但仍然存在零偏和噪声，校准后也不能视为完全准确。

因此，当前项目可以利用 MPU6050 获取角速度，并估计相对稳定的俯仰角和横滚角；对于偏航角，则需要明确其长期漂移的限制。

## 5. 有时效性数据的统一组织方式

对于传感器测量这类具有时效性的数据，我打算统一使用结构体描述一份样本，按以下顺序组织成员：

| 成员 | 当前对应字段 | 表达的含义 |
| --- | --- | --- |
| 本次采集的数据 | `data` | 已完成单位换算和校准的测量值 |
| 时间戳 | `timestamp_us` | 本份样本对应的读取开始时间，单位为微秒，不是芯片内部采样时刻 |
| 发布序号 | `sequence` | 软件成功发布样本的序号，用于识别是否出现新样本 |
| 有效标志 | `valid` | 模块当前是否允许使用这份样本 |

**时间戳描述时间位置，序列号描述发布身份和顺序。** 时间戳可以用于计算样本年龄、判断新鲜度，以及计算两次采集的时间间隔；序列号可以用于避免重复处理同一份样本，并判断两次观察之间发生了多少次发布。

序列号只在软件成功发布样本时递增，不等于芯片内部的采样次数。`valid` 也不单独保证样本新鲜：当前超时检查发生在 `SensorApp_Poll()` 中，消费者判断数据是否过期时，仍需使用同一时间基准比较当前时间与样本时间戳。

## 6. 模块状态管理的工程约定

对于需要实时采样、持续更新数据的模块，除了保存测量值，还应明确记录模块的运行状态，供其他模块判断数据是否可用、设备是否正常。

我打算在项目中形成以下工程习惯：

- 对于具有持续运行状态的模块，使用专门的状态结构体集中管理状态信息。
- 使用带有 `status` 前缀或后缀的变量名；在模块内部语义明确时，直接使用 `status`。
- 状态由所属模块维护，其他模块通过公开的只读接口获取，避免直接修改其内部状态。

在当前实现中，需要区分**模块运行状态**与**样本自身的状态**：

| 类型 | 主要内容 | 用途 |
| --- | --- | --- |
| `SensorStatus` | 是否就绪、采集成功与失败次数、操作结果及底层错误快照 | 查看模块运行情况与诊断信息 |
| `ImuSample` | 测量值、时间戳、发布序号、有效标志 | 判断具体样本的内容、新旧和有效性 |

`ready` 表示模块已准备好、可以尝试采集，不表示当前一定有新鲜样本。`reason` 与 `bus_error` 一起保存最近一次被记录操作的诊断快照，供后续查看；成功操作也会覆盖它们，因此它们不是完整的故障历史。

这种划分让其他模块能够分别判断采集能力、操作结果和样本可用性。

## 7. `sensor_app` 的职责与边界

当前模块承担以下任务：

1. **初始化与重连**：绑定总线和时钟函数，调用 MPU6050 驱动完成设备初始化，并维护相应状态。
2. **管理校准参数**：保存并校验外部传入的零偏与比例系数，采集时应用这些参数；模块本身不执行自动校准。
3. **采集并发布样本**：检查数据就绪情况，读取原始数据，完成单位换算和校准，更新最新样本及其时间戳、序列号和有效标志。
4. **维护状态与诊断信息**：记录采集成功和失败次数，并保存操作结果与底层错误快照。
5. **提供只读访问接口**：通过函数返回内部样本和状态结构体的只读指针，供外部模块使用。

外部获得的是内部存储的地址，不是独立的数据副本。下一次更新会改变该地址中的内容；如果消费者需要保留某一时刻的样本，应自行复制。当前接口约定仅在主循环中串行访问。

模块对外只提供 `SensorApp_Poll()` 作为采集推进入口，由主循环持续调用。`Poll()` 管理采集频率、计划时间和样本超时；到期后调用模块内部的 `static SensorApp_Update()`，完成一次数据更新。错过多个周期时只尝试一次，不补读历史帧。初始化或重连完成后等待一个周期再采集。

主循环决定模块之间的执行顺序，不维护传感器的采集计划。`SensorApp_TimeUntilSampleUs()` 只提供距下次采集的时间余量，不触发更新。姿态解算、控制、显示和日志由各自模块承担。

时间来源通过初始化参数注入：模块保存返回 `uint32_t` 微秒时间的函数指针，在需要的位置获取时间，不直接依赖 DWT 或 `Timebase_NowUs()`。调用者负责准备时钟，并保证消费者使用同一时间基准。
