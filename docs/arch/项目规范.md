# 项目模块设计规范

今后的项目中，对于传感器模块，以及持续生产具有较强时效性数据的模块，采用以下设计规范。

## 1. 分别维护数据与状态

模块内部使用两个职责明确的结构体变量，分别保存**对外发布的数据样本**和**模块运行状态**。

### 1.1 数据样本结构体

一份样本按以下顺序组织：

| 成员 | 含义 |
| --- | --- |
| 数据 | 本次采集或计算得到的结果 |
| 时间戳 | 这份数据对应的测量或事件时间，需明确单位和时间基准 |
| 序列号 | 成功发布的样本序号，用于识别新样本和避免重复处理 |
| 有效标志 | 模块当前是否允许使用这份样本 |

数据及其时间戳、序列号应属于同一次发布。更新失败时，不应仅刷新时间戳或序列号，将旧数据误标记为新数据。

有效性与新鲜度需要区分：有效标志表达模块对样本的判断，消费者还应按需要结合当前时间与时间戳检查数据是否过期。

### 1.2 模块状态结构体

状态结构体类型采用“模块名 + `Status`”的形式命名，例如 `SensorStatus`、`MotionAppStatus`。

状态结构体用于对外说明模块的运行情况，包括是否正常工作、当前等待或失效的原因，以及必要的成功和失败统计。模块运行状态与样本有效性应分别表达，避免重复维护含义相同的字段。

数据和状态均由所属模块维护，通过只读接口供外部访问。需要修改内部配置时，应使用专门的接口进行检查和更新。

## 2. 分开组织更新与轮询

模块内部将单次更新流程与更新触发逻辑分开，分别由 `Update()` 和 `Poll()` 承担。

| 函数 | 职责 | 访问范围 |
| --- | --- | --- |
| `Update()` | 集成一次完整的数据更新流程，包括必要的输入检查、读取或计算、结果发布及状态记录 | 模块内部使用，以 `static` 限定，不在头文件中公开 |
| `Poll()` | 判断是否允许更新、何时调用 `Update()`，并执行超时检查等运行维护逻辑 | 对外公开，由主循环或调度层持续调用 |

`Poll()` 的触发条件可以是周期到达、新输入产生，或两者同时满足，具体取决于模块的职责。未满足条件时可以直接返回；一次轮询不等于一次数据更新。

`Update()` 不负责周期管理，但仍需检查完成本次操作所必需的条件。例如，传感器更新仍需确认设备是否就绪、是否存在可读取的新数据。

轮询中的附加逻辑应限于本模块的运行管理，不应混入其他模块的显示、日志或控制任务。



如果一个数据模块A要依赖另一个数据模块B的数据来计算，则要在数据模块中记录好源自B模块数据的序列号和时间戳，方便溯源。
同时依赖多模块数据的上层算法，也要留好各个模块的时间戳和序列号，方便溯源
