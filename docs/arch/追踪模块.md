# 追踪模块（Trace）架构

## 1. 设计目的

Trace 有两个主要用途：记录运行数据，供后续导出分析；保存异常发生前后的信息，帮助定位问题。

MCU 内存有限，每个记录对象只能分配较小的数组，保留的往往只是很短一段时间。因此使用环形缓冲区持续保存近期数据，并在业务停止或异常时冻结，避免有价值的现场被后续数据覆盖。

## 2. 职责边界

Trace 不需要理解被记录结构体的成员。只要知道源变量地址和数据大小，就可以把当前内容复制到记录数组中。但它无法自行判断哪些字段值得记录，也无法理解各个业务模块的工作状态。

因此，将通用记录机制与项目相关的适配分开：

| 层级 | 负责的事情 | 不承担的事情 |
| --- | --- | --- |
| 通用 Trace | 定频复制、环形覆盖、记录状态管理、终止快照、冻结与读取 | 解释业务字段、采集硬件、计算控制输出 |
| 业务适配 | 准备记录变量，将业务状态转换为统一记录条件 | 管理环形数组和写入位置 |
| 统一管理 | 注册记录对象、源地址、频率和适配函数，组织初始化与轮询 | 替代各业务模块管理自身数据 |

具体记录内容本来就是根据项目需要编写的，不要求这部分适配代码能直接复用到所有项目。真正需要统一的是记录接口和数组管理方式。

Trace 的冻结只停止记录，不代表小车已经停机。启动业务、修改参数、结束试验等行为属于上层试验或任务管理。

## 3. 注册一份记录对象

一份记录对象至少需要以下信息：

| 注册项 | 含义 |
| --- | --- |
| 记录数组地址 | 快照最终保存在哪里 |
| 数组容量 | 最多容纳多少条记录；与字节数区分 |
| 源变量地址 | 本次记录时从哪里读取数据 |
| 单条数据大小 | 每次需要复制多少字节，通常使用 sizeof 获取 |
| 记录频率 | 正常工作时，希望多久保存一次 |
| 状态检测函数指针 | 判断被观察业务是否允许继续记录 |

只传变量地址是不够的，C 语言无法通过地址推断结构体大小。当前实现还登记源/数组的字节数、帧大小、载荷偏移、来源 ID、格式版本和回调上下文，用于边界检查、有类型帧布局及导出识别。

每个实例独立维护数组、写入位置、有效记录数量、计时信息和冻结状态，不使用动态内存分配。

## 4. 数据准备与状态检查分开

### 4.1 源变量负责说明“记录什么”

如果需要完整记录某个已有变量，可以直接注册它的只读地址。若要将样本、工作状态或诊断字段放在一起，则由业务适配代码准备一个专门的记录变量。

例如，LQR 的记录变量可以包含本次控制结果、样本时间与序号、输入来源和必要的诊断信息。通用 Trace 只复制这个变量，不负责挑选字段，也不推断各字段的含义。

源变量必须在本轮记录前更新好。当前管理层先调用 Prepare 函数，再调用通用 Trace 的 Poll；Prepare 不是通用记录器的回调。

### 4.2 检测函数负责说明“是否继续记录”

项目中的业务模块已经维护工作状态，并提供只读查询接口。适配函数读取这些状态，再转换为 Trace 约定的统一结果；随后将检测函数指针注册给记录器。

```c
typedef struct {
    TraceSourceState state;
    uint32_t faults;
} TraceSourceStatus;

typedef TraceSourceStatus (*TraceCheckSource)(void *context);
```

检测函数只查询状态，不采集硬件、不控制业务，也不负责填充记录载荷。

不能简单地把所有情况压成“正常/异常”两个值，因为尚未启动、等待首份数据和运行中发生故障，需要不同的处理方式。

| 检测结果 | 含义及处理 |
| --- | --- |
| STOPPED | 尚未观察到业务开始时等待；开始后停止，则保存现场并冻结 |
| WAITING | 业务已开始但尚无首份数据；准备阶段等待，已经记录后出现则按无效处理 |
| NORMAL | 正常工作，允许检查记录周期 |
| FAULT | 保存故障现场并冻结 |
| INVALID | 保存无效现场并冻结 |

`faults` 保存适配层报告的原因位，非零时优先按故障处理。具体如何把 LQR、IMU 等模块的状态映射到这些结果，由各自的适配代码决定。

## 5. 轮询与记录频率

每轮轮询的顺序是：

```text
外部准备记录变量
        ↓
Trace 查询业务状态
        ├─ 尚未开始或等待首份数据 → 返回
        ├─ 业务结束、故障或无效 → 保存当前快照 → 冻结
        └─ 正常 → 判断记录周期 → 到期后复制到数组
```

状态检查每轮执行，不受记录频率限制。例如以 50 Hz 记录时，也不应该等满 20 ms 才发现异常。

正常记录依据 Trace 自己的周期，不依赖业务样本序号：

- 记录频率高于业务更新频率时，允许多次保存同一份业务数据。
- 记录频率低于业务更新频率时，可能跳过中间样本。
- 业务序号可以随载荷保存，供事后分析，但不用于通用 Trace 去重。

第一份正常数据立即记录，之后按实际记录时间计时。当前周期为 `ceil(1000000 / frequency_hz)` 微秒，允许配置 1 至 1000000 Hz；实际可达到的频率受主循环限制。

主循环延迟时，只保存恢复执行后看到的当前值，不补写多份相同数据来冒充过去的观测。Trace 是定频观察工具，不保证捕获每份业务样本或所有短暂变化。

## 6. 记录器状态与异常现场

记录器自身维护以下状态，与被观察业务的状态分开：

| 状态 | 含义 |
| --- | --- |
| IDLE | 初始化完成，尚未准备记录 |
| ARMED | 已准备，等待业务开始和首份数据 |
| RECORDING | 正在记录 |
| FROZEN | 记录已冻结，等待读取或显式重新准备 |

Arm 重置本次会话的逻辑记录范围，不需要清零整个数组。冻结后不再更新源快照、查询业务状态或改写记录；业务恢复不会自动解冻，必须显式 Arm。

发现停止、故障、无效或手动冻结请求时，绕过正常周期限制，再保存一次当前快照和终止信息，然后冻结。这会占用一条记录；若数组已满，就覆盖最旧的一条。

异常快照不一定包含错误计算的中间结果。按照项目规范，业务更新失败时可能保留上一次成功样本，因此现场可能是“上一份成功数据＋当前错误原因”。如果需要分析被拒绝的输入或失败候选，业务模块必须显式暴露相关诊断信息，Trace 不能还原没有保存的数据。

## 7. 观察时间与业务时间

两类时间和序号必须分开：

| 信息 | 含义 |
| --- | --- |
| 记录头 timestamp_us | Trace 实际保存本次观察结果的时间 |
| 记录头 sequence | 本次记录会话中的记录序号 |
| 载荷 sample_timestamp_us | 被记录业务样本自身的时间 |
| 载荷 sample_sequence | 被记录业务样本自身的序号 |
| 载荷 sample_valid | 业务模块对该样本有效性的判断 |

同一业务序号出现在多条记录中，并不一定是异常，可能只是 Trace 的观察频率更高。终止帧的 `header.valid=0` 表示它不是正常记录，不能据此认为该帧没有载荷；载荷仍保存终止时的源变量。

时间由外部通过参数传入，使用统一的 uint32 微秒基准，支持自然回绕。

## 8. 环形存储与访问约定

写入位置指向下一条记录的位置。数组未满时增加有效记录数量，写满后覆盖最旧记录；读取接口在冻结后按时间顺序返回副本。

- 源变量和记录数组必须在整个记录期间持续有效，不能注册短生命周期局部变量。
- 源变量不能与记录数组重叠，实例之间不共享写入存储。
- 实例初始化后不直接复制，否则内部地址可能继续指向原实例的数组和源变量。
- 当前数据准备、状态检查和复制均在主循环中串行执行；中断或多任务并发修改源数据时，需要额外解决一致性问题。
- 对外提供只读查询和受控操作接口，不通过暴露可写业务指针来控制被观察模块。

## 9. 与原有方案的区别

原有 Trace 通过一个快照回调同时取得载荷和业务状态，按业务新序号记录，并在终止事件中只保存事件头。

现在的方案保留必要的业务生命周期判断，但改变了数据获取和记录机制：

| 原有方案 | 当前约定 |
| --- | --- |
| 回调同时组装数据和报告状态 | 源地址提供数据，独立检测函数报告状态 |
| 按业务新序号记录，跳过重复样本 | 按指定频率观察，允许重复记录 |
| 正常记录头使用业务时间和序号 | 记录头使用观察身份，业务身份放在载荷中 |
| 终止事件不复制业务载荷 | 额外保存当前快照，再冻结 |

设计重点不是删除所有状态，而是让通用层只保留明确需要的机制，具体数据含义与业务判断留给项目适配层。
